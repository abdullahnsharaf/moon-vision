# Moon Vision 🌙

A website where you **take or upload a photo of the Moon**. A computer-vision pipeline then
**classifies its phase** (8 classes) and estimates **how bright it is** in three ways.

```
browser (camera / file)  ──►  FastAPI  ──►  1. segmentation + disk fit   (OpenCV)
                                            2. CNN phase classifier      (ONNX)
                                            3. fusion → phase class
                                            4. brightness A / B / C
```

## Quick start

```bash
pip install -r requirements.txt
uvicorn backend.app:app --reload --port 8000   # from the project root
# open http://localhost:8000
```

To use the camera from a phone, the page has to be served over **HTTPS** (browsers block
`getUserMedia` on plain http except on `localhost`). For phone testing, run the server on your
laptop and expose it with `ngrok http 8000` or `cloudflared tunnel`. Or use the
"Snap with phone camera" link, which opens the phone's camera app through a normal file input.

## Deploy on Vercel

The project is already set up for Vercel's zero-config FastAPI support:

* `pyproject.toml` points Vercel at the app (`[tool.vercel] entrypoint = "backend.app:app"`) and
  lists the **runtime** dependencies only. PyTorch isn't included: training happens on your own
  machine with `requirements-train.txt`.
* `.vercelignore` leaves out training, tests and screenshots.
* `vercel.json` gives the function up to 30 s.
* Vercel limits a request to 4.5 MB, so the browser shrinks big photos (max 2048 px) before
  uploading and sends the photo's shutter, aperture and ISO as separate fields, because
  shrinking strips them from the file.

**Option A – GitHub (recommended)**
1. Push the `moon-vision` folder to a new GitHub repository.
2. On vercel.com: *Add New → Project → Import* that repository.
3. Leave Framework preset on what it detects (FastAPI / Python) and the root directory as `./`. Click **Deploy**.
4. Every `git push` redeploys automatically.

**Option B – Vercel CLI**
```bash
npm i -g vercel
cd moon-vision
vercel          # first time: log in, accept the defaults -> preview URL
vercel --prod   # production URL
```

Check it works: open `https://<your-project>.vercel.app/api/health`. It should return
`"cnn_loaded": true`. The live-camera tab works on phones because Vercel serves HTTPS.

## Interface

* **English and Arabic.** Use the switch at the top right. Arabic gets a full right-to-left layout
  with Reem Kufi and IBM Plex Sans Arabic fonts. The choice is remembered, and the page starts
  in Arabic when the browser language is Arabic. All strings live in `frontend/i18n.js`. To add a
  language, copy the `en` block. The API returns codes (`warning_codes`,
  `waxing_decided_by_code`) so the page can translate them.
* **The dial.** The moon sits inside an astrolabe-style ring graduated in elongation (0° new,
  90° first quarter, 180° full, 270° last quarter). While idle it slowly cycles through a whole
  lunation. While analysing it sweeps like a scanner. When the result arrives it turns to the
  measured phase, and the pointer marks that point in the lunar cycle.
* **Lottie animations.** `frontend/lottie/idle.json` (empty upload box) and `scan.json` (progress
  panel) are generated by `tools/make_lottie.py` and played by the bundled `lottie-web` player
  (`frontend/vendor/`, MIT licence), so they work offline. To use animations from LottieFiles
  instead, download their JSON into `frontend/lottie/` and keep the same file names.
* Animated starfield with occasional meteors, count-up numbers, growing probability bars, and
  an analysis progress list. Everything respects the operating system's *reduce motion* setting.

## How the phase is found

| Step | What happens | File |
|---|---|---|
| Segmentation | grey → Otsu threshold (with a percentile floor) → brightest compact blob → fill holes | `moon_cv/segment.py` |
| Disk fit | The two cusps of the terminator are always **diametrically opposite**, so the farthest pair of lit points gives a first centre and radius. This is then refined by a least-squares circle fit on the **limb** points only. That recovers the *whole* disk, dark part included. | `segment.py:fit_disk` |
| Lit fraction | `k = lit pixels / (π r²)` | |
| Lit side | angle from the disk centre to the centroid of the lit area | |
| CNN | small 5-block CNN on a 128×128 crop around the disk → 8-class softmax | `moon_cv/cnn.py`, `training/train.py` |
| Fusion | both experts are reduced to *band* (new / crescent / quarter / gibbous / full) × *waxing probability*, then averaged | `moon_cv/analyze.py` |

Phase bands by lit fraction: new < 3 % · crescent 3–40 % · quarter 40–60 % · gibbous 60–97 % · full ≥ 97 %.
You can change them in `astro.py`.

**Everything comes from the picture.** No date or calendar is used.

**Waxing or waning?** Read from which side of the disk is lit, which depends on where the photo was taken:

* **Northern Hemisphere** (default) – lit on the right = waxing
* **Southern Hemisphere** – lit on the left = waxing (the crop is mirrored before the CNN)

Near the equator the crescent can lie almost on its back, so waxing vs waning is less certain
there. The crescent/quarter/gibbous/full part of the answer is unaffected.

## Brightness – three methods

| | Method | Output | Strength | Weakness |
|---|---|---|---|---|
| **A** | **Class reference** (your idea 1) – look up the range for the predicted class using the lunar phase law `m = −12.73 + 0.026·α + 4·10⁻⁹·α⁴` (Allen / Cox 2002) | magnitude range, lux range, % of full | simple, standard references | coarse – every crescent gets the same range |
| **B** | **Pixel measurement** (your idea 2) – undo sRGB gamma and measure the lit pixels inside the mask: mean, p95, integrated flux, contrast vs sky, clipping % | relative index; **cd/m²** if EXIF has shutter/aperture/ISO (`L = K·N²/(t·S) · v/0.18`) | uses the actual photo; heat-map | depends on exposure, phone HDR, clouds; overexposed pixels clip |
| **C** | **Photometric model** (new) – the *measured* lit fraction → phase angle `α = arccos(2k−1)` → magnitude → illuminance `E = 2.54·10⁻⁶ · 10^(−0.4 m)` lux, at the mean Earth–Moon distance | magnitude, lux, % of full | continuous like B, camera-independent like A | assumes a clear sky (no atmospheric extinction) |

Brightness falls off much faster than lit area. A half Moon is ~50 % lit but only ~9 % as
bright as a full Moon, because of shadows and the opposition surge.

## The CNN – please retrain it on real photos

`backend/models/moon_phase.onnx` was trained **only on synthetic renders**
(`training/synth.py`: a Lommel-Seeliger lit sphere, random maria/craters, rotation, glow,
blur, noise, overexposure, JPEG). It works on clean photos, but real photos have clouds,
trees, city lights and phone HDR, so for good accuracy:

1. Collect real photos into `data/real/<class>/` using the 8 class names:
   `new_moon waxing_crescent first_quarter waxing_gibbous full_moon waning_gibbous last_quarter waning_crescent`.
   Sources: your own photos (labelled by hand or with a moon-phase calendar), or public sets such as the Roboflow Universe "Phase Your Moon" dataset
   (8 classes) or Kaggle moon-phase datasets. Check each one's licence.
2. `python training/train.py --real data/real --synthetic 800 --epochs 20`

Training crops real photos with the same segmentation the website uses, so training and
inference see the same input. **Don't add horizontal flips** as augmentation: they swap waxing
and waning.

## Project layout

```
backend/
  app.py                 FastAPI server (also serves the frontend)
  moon_cv/segment.py     segmentation + limb disk fit
  moon_cv/cnn.py         ONNX inference
  moon_cv/analyze.py     fusion, EXIF, orchestration
  moon_cv/brightness.py  methods B and C + visualisations
  moon_cv/astro.py       phase classes + phase law (method A)
  models/                moon_phase.onnx + .json
frontend/                index.html, style.css, app.js, i18n.js, lottie/, vendor/, samples/
tools/make_lottie.py     generates the Lottie animations
training/synth.py        synthetic moon renderer
training/train.py        CNN training + ONNX export
tests/test_pipeline.py   accuracy check on synthetic photos
```

## Ideas for next steps

* Swap the small CNN for a pretrained MobileNetV3 / EfficientNet backbone once you have real data.
* Train a U-Net for segmentation if thresholding fails on cloudy photos.
* Add atmospheric extinction to method C using the Moon's altitude (needs location + time).
* Deploy: Render / Railway / Hugging Face Spaces (Docker) for the backend.
